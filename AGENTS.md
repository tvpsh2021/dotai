## Coding Style Conventions

Apply to Node.js, JavaScript, and TypeScript

- **File Naming**: Use kebab-case for file names.
- **Variable Naming**: Use `const` and `let` instead of `var`. Use camelCase for variables and functions.
- **Function Naming**: Use camelCase for function names.
- **Class Naming**: Use PascalCase for classes and constructors.
- **Constant Naming**: Use UPPER_CASE for constants.
- **Commenting**: Add meaningful JSDoc comments for function if needed, otherwise don't write too many comments.
- **Error Handling**: Use try/catch blocks for error handling.
- **Logging**: Do not write meaningless logs. Only log meaningful events, errors, and important state changes.
- **Testing**: Use Jest for testing.
- **Indentation**: Use 2 spaces for indentation.

## Performance & Concurrency Guidelines

- **Concurrency control for `Promise.all()`**: Before using `Promise.all()`, assess whether the number of concurrent operations is bounded. If the input array size depends on external data (e.g., a list from DB query results or request payload), the count could be larger than expected at runtime. In such cases, use a concurrency limiter (e.g., `p-limit`) to cap the number of simultaneous operations, especially when each operation involves DB writes, external API calls, or other I/O-heavy work.
- **Thundering herd awareness**: For APIs that may receive sudden bursts of traffic, consider whether the implementation can handle concurrent requests safely without causing cascading load on downstream systems (DB, external services). Flag this concern during implementation if the API is likely to be called at high frequency.
- **Bulk vs. individual operations**: Prefer bulk DB operations (e.g., `updateMany`, `insertMany`, bulk writes) over looping individual writes inside `Promise.all()` when operating on multiple documents.

## Architecture Patterns

- Follow the Controller-Service-Repository pattern regardless of the framework being used
  - Controller: Handle HTTP requests and responses
  - Service: Business logic and orchestration
  - Repository: Data access layer

## Development Workflow

- All code must be tested on localhost before deployment, do not deploy directly without asking the user.
- Never automatically perform `git commit` or `git push` operations.
- Always let the developer manually review and commit changes.
- Only suggest commit messages when explicitly asked.
- Commit Messages should follow the Conventional Commits specification. Keep the subject line under 72 characters.
- Keep project's `README.md` documentation file updated with any new features or changes.
- **Test file updates**: Whenever implementation code is changed, always check for a corresponding test file (e.g., `*.spec.ts`) and update it in the same task. This includes updating mocks, assertions, and test descriptions to reflect the new behavior. Do not treat test updates as a separate follow-up step.
